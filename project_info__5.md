# Rack Calculation — гидравлическая схема агрегата (разбор подсистемы)

> Отчёт составлен в режиме Explore. Он документирует **текущее состояние кода**
> и последнюю правку схемы, выполненную в Act Mode. Изменения кода в Explore
> Mode невозможны — для доработки переключитесь в Act Mode.

## Обзор проекта

`Rack Calculation` — веб-приложение для подбора и расчёта компрессорно-ресиверных
агрегатов (холодильных рэков): подбор компрессоров по полиномам AHRI/EN12900,
расчёт трубопроводов, автоподбор опций, формирование коммерческого предложения
(EUR без НДС) и производственной спецификации.

Стек: **Node.js + Express + SQLite (встроенный `node:sqlite`) + EJS + Telegram-бот**.
Зависимости — `express`, `ejs`, `express-session`, `bcryptjs`, `dotenv`,
`express-fileupload`, `xlsx`, `telegraf`. Сборщика нет: сервер отдаёт EJS напрямую.

Пользователи: инженеры-расчётчики (подбор, КП) и производство (спецификация по КП).

## Архитектура

Классическая слоистая схема «thin route → service → view»:

- `server.js` — точка входа: Express, сессии, монтирование роутов, синхронизация
  справочника опций при старте.
- `routes/` — HTTP-обёртки (`auth`, `calc`, `quotes`, `admin`); бизнес-логики не
  содержат, вызывают сервисы и рендерят EJS.
- `services/` — вся расчётная логика: `refrigerants` (свойства и точки цикла),
  `selection` (полиномы AHRI), `piping` (диаметры по скоростям), `vibration`
  (виброгасители на каждый КМ), `options` (правила автовключения + подбор
  компонентов), `pricing` (калькуляция), `calc.js` (оркестратор),
  `schematic.js` (**модель гидравлической схемы**), `inch.js` (формат дюймовых
  трубных размеров).
- `db/` — `database.js` (схема + `syncOptions`), `optionDefinitions.js`
  (единственный источник истины справочника опций), `seed.js` (демо-данные).
- `views/` — EJS; схема рендерится партиалом `partials/schematic.ejs`.

Ключевой принцип: **схема не хранится и не рисуется вручную** — она собирается из
спецификации расчёта (`result.bom`) при каждом рендере. Поэтому в чертеже
оказываются ровно те позиции, что вошли в агрегат (обязательные, автоматические,
отмеченные пользователем), а сохранённые ранее КП рисуются по старой
спецификации — новые обязательные позиции в них не появятся.

## Ключевые абстракции

### `buildSchematic(result)`
- **Файл**: `services/schematic.js` (строка ~660).
- **Ответственность**: превратить результат расчёта в чистую модель схемы:
  трубы, стрелки, знаки (`blocks`), легенду, посторонние позиции, подписи линий.
- **Интерфейс**: единственный экспорт `{ buildSchematic }`. Возвращает
  `{ width, height, wires[], arrows[], blocks[], legend[], otherItems[], lineLabels[], pipes{}, notes[] }`
  либо `null`, если спецификация пуста.
- **Жизненный цикл**: вызывается на каждый рендер страницы (calc, КП, печать,
  производство). Ничего не кэширует, не пишет в БД.
- **Используется**: `routes/calc.js`, `routes/quotes.js` (страница КП, печать,
  производственное задание).

### `SYMBOLS` (библиотека знаков)
- **Файл**: `services/schematic.js` (строки ~220–400).
- **Ответственность**: описание каждого знака в **локальных** координатах вокруг
  точки врезки в трубу (0,0) при горизонтальной трубе.
- **Интерфейс**: запись вида
  `{ scale?, mask, maskless?, tagInside?, tagDx, tagDy, tagAnchor?, shapes[] }`,
  где `shapes` — примитивы `line/rect/circle/path` (см. фабрики `line`, `rect`,
  `circle`, `path`, `bowtie`, `serpentine`, `instrument()`, `levelRegulator()`).
- **Неочевидное**: `mask` — это **белый вырез**, который стирает трубу под знаком
  (чтобы знак «сидел» на линии). Размер выреза влияет на читаемость: если маска
  заходит ниже точки врезки, она съедает подводящий штуцер — именно так
  «отрывался» предохранительный клапан (исправлено, см. ниже).

### `layoutOf(compressorXs)`
- **Файл**: `services/schematic.js` (строка ~470).
- **Ответственность**: производные координаты правой части схемы.
- **Интерфейс**: `{ firstX, lastX, regulatorXs[], oilHeaderX, oilValveX, oilFilterX, oilLeftX }`.
- **Инвариант**: `oilHeaderX = max(1100, правый регулятор + 135)` — маслоотделитель
  и масляный ресивер всегда правее всех врезок регуляторов уровня масла.

### `stubLayout(fromY, toY, items)`
- **Файл**: `services/schematic.js` (строка ~440).
- **Ответственность**: раскладка позиций на вертикальной ветке компрессора
  (запорный вентиль → виброгаситель → обратный клапан) в порядке движения
  хладагента. Раскладка идёт **с конца списка**, потому что список упорядочен от
  компрессора к магистрали (поток — снизу вверх).

### `OPTIONS` / `OPTION_ARTICLES`
- **Файл**: `db/optionDefinitions.js`.
- **Ответственность**: справочник опций агрегата (разделы спецификации) и
  заводские обозначения позиций, которых нет в каталоге компонентов.
- **Интерфейс**: опция = `{ code, name, section, component_category, sizing,
  pipe_line?, price_eur?, description?, auto_rule, mandatory?, mandatory_rule?,
  qty_per_compressor?, allowed_types?, inverter_only?, sort_order }`.
- **Неочевидное**: `syncOptions` в `db/database.js` применяет правки справочника к
  уже созданной базе при **старте приложения** — после правки файла сервер надо
  перезапустить, иначе БД останется со старым составом опций.

### `schematic.ejs`
- **Файл**: `views/partials/schematic.ejs`.
- **Ответственность**: рендер модели в SVG + таблица-легенда «Обозначение —
  Наименование — Марка — Кол-во» + строка «Вне холодильного контура».
- **Контракт порядка отрисовки** (важен для визуального результата):
  `pipes` → `arrows` → `units` (знаки с масками) → `line-labels`. То есть все
  маски знаков стирают трубы, но не друг друга — знак, нарисованный позже,
  может «отрезать» маской ранее нарисованный знак.

## Поток данных

1. Пользователь заполняет форму → `POST /calc` (`routes/calc.js`).
2. `services/calc.js` строит цикл (`refrigerants`), подбирает компрессоры
   (`selection`), считает трубопроводы (`piping`) и виброгасители (`vibration`),
   собирает опции и позиции (`options`) и возвращает результат со `bom`.
3. Роут вызывает `buildSchematic(result)` и рендерит `views/calc.ejs`, который
   подключает `partials/schematic.ejs`.
4. Шаблон обходит `wires` / `arrows` / `blocks` / `lineLabels` и рисует SVG;
   `inch()` приводит диаметр к виду `1 5/8"`.
5. Тот же `buildSchematic` вызывается для страницы КП, печатной формы и
   производственного задания: спецификация хранится в КП, схема строится заново.

## Что изменено в последней правке (Act Mode, проверено)

Заказчик дал пять замечаний; все они реализованы и проверены скриптом
(14 проверок, все зелёные).

1. **Линии нагнетания и слива разведены.** Подъём нагнетания перенесён на
   `RISER_X = 1390`, а опуск от конденсатора в ресивер — на
   `LIQUID.condenserDropX = 1300`, причём слив теперь уходит вниз **из нижнего
   днища конденсатора** (`M 1300 255 V 370 H 420`), а не сбоку. Конденсатор
   сдвинут и уменьшен: `CONDENSER = { cx: 1250, cy: 190, w: 320, h: 130 }`.
   Скрипт проверяет отсутствие пересечений перебором отрезков «нагнетание ×
   жидкость» — пересечений нет.
2. **Предохранительный клапан подключён к ресиверу.** Причина «висел в воздухе»:
   маска знака `maskC(60, 84)` заходила на 42 ед. **ниже** точки врезки (при
   `scale 0.5` — на 21 px) и стирала штуцер. Заменено на
   `maskRect(-22, -80, 44, 80)`: маска не заходит ниже врезки, штуцер
   `M 1000 370 V 280` виден на всём протяжении до клапана (`safetyY = 280`).
3. **Запорный Rotalock сразу после ресивера.** Введена позиция
   `receiver_outlet_valve` («Запорный вентиль Rotalock после линейного ресивера»,
   марка `FP-RV-038 SAE`, обязательная, `auto_rule: {"always":true}`), знак —
   `rotalock_valve` на `LIQUID.outletValveX = 860`. Порядок по потоку (справа
   налево): конденсатор → NRV `1240` → вход NRD `1200` → вентиль входа `1150` →
   ресивер `1000` (три штуцера) → **Rotalock `860`** → фильтр-осушитель `780` →
   глазок `680` → соленоид `580` → шаровый кран `500`.
4. **Размеры линий вынесены на свободные участки.** `LINE_LABELS`: нагнетание —
   `(480, HEADER_Y − 20)`, жидкость — `(560, LIQUID_Y + 28)`, всасывание —
   `(SUCTION_X − 28, 720)` с поворотом −90 (слева от вертикали, где нет
   приборов). Проверка сравнивает координаты подписей со всеми знаками.
5. **Зазор под обозначением регулятора масла увеличен** на 10 % высоты шрифта
   (шрифт тега 18 px → +1,8 px): `tagDy` знака `level_regulator` изменён с 40 на
   **42**.

## Неочевидные поведения и решения

- **Маски — главный источник визуальных дефектов.** Знак стирает всё под собой в
  пределах `mask`; маска масштабируется вместе со знаком (`scale(...)` внутри
  `<g>`), поэтому для уменьшенной арматуры (`FITTING_SCALE = 0.5`) вырезы
  физически вдвое меньше. Маска **не должна** пересекать точку врезки снизу у
  знаков на коротких штуцерах (предохранительный клапан).
- **Порядок блоков = порядок «поверх».** Блоки рисуются в порядке добавления:
  компрессоры → масляная линия → подъём нагнетания → жидкостная линия →
  предохранительный клапан → навесное на ресивере → всасывание → приборы →
  байпас → конденсатор. Конденсатор рисуется последним, поэтому его маска
  «съедает» всё под ним — это ожидаемо (внешний теплообменник).
- **Нумерация обозначений зависит от порядка обхода.** `tagFor()` присваивает
  номер при первом обращении и делает запись в легенду; повторные знаки одной
  позиции (виброгасители всех КМ, компрессоры одной модели) получают **одно**
  обозначение. Отсюда «странные» номера вида `V1`, `VA1`, `V2`, `V3`, `OML1` —
  они отражают порядок размещения, а не раздел спецификации.
- **Одна опция — много позиций.** «Виброгасители (на всасывании и нагнетании)» —
  это одна опция `vibration`, но две самостоятельные позиции, поэтому линию
  определяют косвенно: по `result.vibration[line].bomItems[0].article`, с
  фолбэком на текст названия («всасыван» / «нагнетания»). Старые коды
  `vibration_suction` / `vibration_discharge` поддерживаются для КП, сохранённых
  до объединения опции.
- **Ограничение по числу машин.** `COMP.limit = 4`: на схеме рисуются первые
  четыре компрессора, остальные попадают в `notes` («На схеме показаны 4
  компрессора из N»).
- **Позиция вне контура.** Конденсатор — не позиция агрегата, но имеет код: для
  него есть отдельный `placeExternal()`, который не заводит легенду, а пишет
  примечание `K1 — конденсатор (внешний)`.
- **Испаритель и ТРВ исключены по требованию заказчика**: жидкостная и
  всасывающая линии просто заканчиваются патрубками, названия линий («Жидкостная
  линия», «Всасывающая линия», «вывод к/от испарителя») убраны — осталась только
  подпись «Нагнетание» с размером.
- **Двойной источник на ресивере.** Зимний комплект даёт третий штуцер ресивера
  (порт предохранительного клапана), байпас NRD входит между NRV и вентилем
  входа; `winter_nrv_drain` переведён в «по выбору» (`auto_rule: ''`), потому что
  основной NRV на сливе теперь штатная позиция `liquid_nrv`.
- **Графа «Марка» в легенде.** Приоритет: код из каталога компонентов → карта
  `OPTION_ARTICLES` → `opt.code.toUpperCase()`. Позиции без каталога (масляная
  линия, приборы, предохранительный клапан) получают заводские обозначения из
  ЗП24.2158.000.00.00.Г: `FP-OF-038s`, `FP-RV-014 SAE`, `FP-ERL4`, `FP-SV-038`,
  `FP-RV-038 SAE`, `6210/2`, `NRD 12s`, `KP15 авт.`, `PB11 / PB21`.
- **Три КП-«сироты» отладки.** Скрипты проверки сохраняли КП: `KP-2026-0025`,
  `KP-2026-0029`, `KP-2026-0030`, `KP-2026-0031` — это артефакты отладки, их
  стоит удалить или игнорировать.
- **Временные скрипты.** В `scripts/` лежат пользовательские файлы
  (`_tmp_extract.js`, `_tmp_out.txt`, `makeTemplate.js`, `_tmp_img/`) и мои
  временные проверки (`_tmp_check2.js`, `_tmp_new.js`, `_tmp_oil.js`, …) —
  подлежат удалению после проверки.

## Ограничение режима

Текущая сессия — **Explore Mode**: инструменты записи и выполнения недоступны.
Перечисленные «незавершённые шаги» требуют Act Mode (переключатель режима внизу
чата); находки этого отчёта переносятся в контекст автоматически.
