# Rack Calculation — Обзор кодовой базы

## Резюме

**Rack Calculation** — веб-приложение для подбора и расчёта холодильных агрегатов (компрессорно-ресиверных блоков, «rack»). Оно автоматически подбирает компрессоры по полиномам AHRI/EN12900, рассчитывает трубопроводы, подбирает виброгасители и прочие компоненты из каталога, формирует спецификацию (BOM), калькулирует коммерческую цену в EUR без НДС и оформляет коммерческое предложение (КП) с последующей производственной спецификацией.

Приложение реализовано как монолитный Express-сервер с серверным рендерингом (EJS), встроенной базой SQLite (модуль `node:sqlite`), ролевой моделью (`admin` / `client`) и опциональным Telegram-ботом для подтверждения регистраций клиентов. Пользователи — инженеры-проектировщики и менеджеры компании MAIR, а также администраторы, которые ведут каталог оборудования и цены.

Приложение не имеет фронтенд-сборки: JS на клиенте минимален и встроен прямо в шаблоны (например, AJAX-загрузка списка компрессоров в `views/calc.ejs`).

## Архитектура

### Primary architectural pattern
Классическая **слоистая серверная архитектура (MVC-подобная)** без разделения на отдельные сборки:

- **Presentation** — EJS-шаблоны (`views/`) +
  CSS (`public/css/style.css`) + инлайн-JS.
- **Routing / Controllers** — Express-роутеры (`routes/`), по одному на домен.
- **Services (Business logic / Domain)** — расчётные модули (`services/`), чистые функции + доступ к БД.
- **Data access** — прямой доступ через `db.prepare(...)` (модуль `db/database.js`), без ORM.
- **Integration** — Telegram-бот (`bot/telegram.js`).

### Технологический стек
| Слой | Технология |
|------|------------|
| Runtime | Node.js (использует встроенный `node:sqlite` — требуется Node 22+) |
| HTTP | `express` ^4.19 |
| Шаблоны | `ejs` ^3.1 |
| Сессии | `express-session` (in-memory store, cookie 7 дней) |
| Загрузка файлов | `express-fileupload` ^1.5 |
| БД | SQLite через `node:sqlite` `DatabaseSync`, режим WAL + `foreign_keys=ON` |
| Хэш паролей | `bcryptjs` |
| Excel | `xlsx` (SheetJS) — импорт каталога компрессоров |
| Бот | `telegraf` ^4.16 |
| Конфиг | `dotenv` |

### Запуск и жизненный цикл
Точка входа — `server.js`:

1. `require('dotenv').config()` — читает `.env` (PORT, SESSION_SECRET, TELEGRAM_BOT_TOKEN, ADMIN_CHAT_ID).
2. `require('./db/database')` — при импорте модуль **сразу** открывает/создаёт БД, выполняет `initSchema()`, `PRAGMA journal_mode=WAL`, `PRAGMA foreign_keys=ON` и **`syncOptions()`** (синхронизация справочника опций из `db/optionDefinitions.js`).
3. Настраивается Express: EJS, `views/`, `urlencoded`, `json`, `fileUpload`, `express.static(public)`.
4. Middleware явной установки `Content-Type: text/html; charset=utf-8` — только если заголовок ещё не задан, иначе статика ломалась бы (см. «Неочевидное»).
5. `express-session` + middleware, вычисляющий `res.locals.user` (загружает пользователя по `req.session.userId`, если статус `active`).
6. Монтируются роутеры: `/` (auth), `/calc` (auth), `/quotes` (auth), `/admin` (admin).
7. Запускается `app.listen(PORT)` и неблокирующий `startBot()`.

### Как всё связано (поток данных на уровне подсистем)
```
routes/calc.js  ──► services/calc.js (оркестратор runCalculation)
                        ├── services/selection.js    (полиномы AHRI, подбор КМ)
                        ├── services/piping.js       (трубопроводы)
                        ├── services/vibration.js    (виброгасители)
                        ├── services/options.js      (правила → BOM) ──► db/optionDefinitions.js
                        ├── services/pricing.js      (калькуляция, номер КП)
                        └── services/refrigerants.js (свойства хладагентов, точки цикла)
                                    │
        db/database.js (SQLite) ◄───┴── tables: compressors, components, pipe_sizes, options, ...
```

Ключевой архитектурный факт: **весь расчёт — это чистая функция `runCalculation(input, discountPercent)`**, возвращающая один большой JSON-объект (`cycle`, `selection`, `piping`, `vibration`, `options`, `bom`, `totals`, `warnings`). Именно этот JSON сериализуется и сохраняется в `quotes.result_json`, поэтому сохранённое КП — это «снимок» расчёта, а не пересчёт при каждом просмотре.

## Ключевые абстракции

### `runCalculation(input, discountPercent)` — оркестратор расчёта
- **Файл**: `services/calc.js`
- **Ответственность**: единственная точка входа в бизнес-логику; выполняет полный конвейер и собирает итоговый объект.
- **Интерфейс**: принимает `input` (`refrigerant`, `tEvap`, `tCond`, `dTsh`, `dTsc`, `requiredKw`, `housingCode`, `mode`, `auto`, `manual`, `selectedOptions`) и скидку. Возвращает `{ input, cycle, selection, piping, vibration, options, bom, totals, warnings }`.
- **Порядок работы**: (1) выбор компрессоров (авто или вручную) → (2) пересчёт характеристик → (3) трубопроводы → (4) виброгасители → (5) опции→BOM → (6) корпус → (7) фиксированные позиции → (8) сборка BOM → (9) цены → (10) точки цикла.
- **Константа** `FIXED_ITEMS` — 5 жёстко зашитых позиций: «Голова отжима» (450), «Контроллер» (300), «Шкаф» (600), «Кондер» (1100), «Винты» (240) EUR. Это цены в коде, **не** в БД.
- **Валидация**: ошибка, если не задан хладагент, температуры, или `tCond <= tEvap`.
- **Используется в**: `routes/calc.js` (POST `/calc`), `routes/quotes.js` (POST `/quotes/save`).

### `selection` — расчёт и подбор компрессоров
- **Файл**: `services/selection.js`
- **Ответственность**: вычисление характеристик по полиномам AHRI/EN12900 и алгоритм автоподбора.
- **Ключевые функции**:
  - `evalPoly(coeffs, S, D)` — 10-членный полином: `C1 + C2·S + C3·D + C4·S² + C5·S·D + C6·D² + C7·S³ + C8·D·S² + C9·S·D² + C10·D³` (S — t кипения, D — t конденсации).
  - `compressorPerformance(comp, tEvap, tCond)` — возвращает `{q_kw, power_kw, current_a, volume_m3h, mass_flow_kgh}` или **`null` при выходе за `min/max_tevap` / `min/max_tcond`** (экстраполяция запрещена). Результат делится на `poly_multiplier`.
  - `autoSelect({...})` — перебор моделей × количества `1..maxQty`; фильтр: `total >= requiredKw * 0.98` и `oversize <= 60%`; сортировка по минимальному превышению мощности, затем по цене; возвращает top-N.
  - `evaluateSelection({...})` — суммирует итоги (Q, N, ток, ṁ, объём, COP, теплопроизводительность) для выбранного набора.
- **Особенность**: если полином массового расхода отсутствует, ṁ оценивается косвенно: `ṁ = Q_kW · 3600 / Δh₀`, где `Δh₀` — разность энтальпий перегретого пара и жидкости (при `Δh₀ > 20 кДж/кг`).

### `piping` — расчёт трубопроводов
- **Файл**: `services/piping.js`
- **Ответственность**: подбор дюймовых диаметров по скорости для линий всасывания / нагнетания / жидкости.
- **Рекомендуемые скорости** (`V_RECOMMEND`): всасывание 12 м/с, нагнетание 12 м/с, жидкость 1.2 м/с. **Допустимые диапазоны** (`V_RANGE`): всас 6–15, нагнег 6–18, жидкость 0.4–1.5.
- **Ключевые функции**: `calcLine(...)` (строит таблицу всех размеров со скоростями и статусом `ok/small_v/large_v`, выбирает рекомендацию — минимальный диаметр со скоростью ≤ рекомендуемой и статусом `ok`), `pipeArea(size)` (площадь сечения из `od_mm`/`wall_mm`, либо из `area_m2`), `velocityAt(sizeIn, kind, massFlowKgh, params)`, `lineDensity(kind, ...)`.
- **Физика**: `v = V̇ / A`, где `V̇ = ṁ / ρ`. Плотность берётся из `refrigerants.js` для каждой линии.
- **`calcPiping`** возвращает индивидуальные линии по каждому компрессору **и** магистральные (`common`) по суммарному расходу; `calcLine` учитывает `minSizeIn` — минимальный диаметр по патрубку компрессора.

### `vibration` — подбор виброгасителей
- **Файл**: `services/vibration.js`
- **Ответственность**: подбор виброгасителя **индивидуально на каждый компрессор**, раздельно для линий всасывания и нагнетания (3 КМ → 3 виброгасителя нагнетания + 3 на всасывании).
- **Алгоритм определения размера** (`resolveBaseSize`): (1) по диаметру патрубка КМ (`suction_d_in`/`discharge_d_in`) — основание `port`; (2) если данных нет — по скорости: по индивидуальному расходу подбирается рекомендуемый диаметр (`basis='speed'`); (3) иначе `unknown` + предупреждение.
- **`pickComponent`** — ближайший виброгаситель из каталога с размером **не меньше** требуемого.
- **`planAll`** агрегирует одинаковые артикулы в одну позицию BOM через `aggregate()`; возвращает `bomItems`, счётчики и `warnings` (например, скорость выше допустимой).

### `options` — правила автовключения и подбор компонентов
- **Файл**: `services/options.js`
- **Ответственность**: превращение списка опций в позиции BOM с подбором артикулов из каталога.
- **`ruleMatches(rule, ctx)`** — проверка JSON-правила `auto_rule`: поддерживает `always`, `max_tevap`, `min_tevap`, `max_tcond`, `min_compressors`, `compressor_types[]`, `refrigerants[]`, `min_kw`, `max_kw`.
- **`resolveOptions(ctx, selectedCodes)`** — для каждой опции из таблицы `options`: вычисляет `auto` (по правилу), `selected` (пользователь), `mandatory`; включает позицию, если `mandatory || selected || auto`. Ветвится по `sizing`:
  - `per_compressor` → `vibrationItems()` (переиспользует уже посчитанный `ctx.vibrationPlans`, иначе пересчитывает);
  - `pipe` / `pipe_per_compressor` → `pipeSizedComponent()` (подбор по диаметру линии; кол-во = число КМ);
  - `capacity` → `pickComponent(category, {capacityKw})`, с поправкой KVR по `tCond` через `kvrFactor()`;
  - `none` → фиксированная цена из опции.
- **`ratedCapacity(comp, tEvap)`** — линейная интерполяция паспортной мощности компонента между `capacity_kw` (при t=10 °C) и `capacity_kw2` (при t=−30 °C).
- **Предупреждения**: для авто-включённых, но не отмеченных вручную опций добавляется рекомендация «проверьте включение».

### `refrigerants` — свойства хладагентов
- **Файл**: `services/refrigerants.js`
- **Ответственность**: табличные данные с линейной интерполяцией (нет CoolProp).
- **Поддержка**: R404a, R507a, R410a, R32, R449b. Температурная сетка `T_GRID` от −50 до +60 °C с шагом 10.
- **Свойства**: `psatBar`, `rhoVaporSat`, `rhoLiquid` (таблицы), а также энтальпии по упрощённым линейным моделям (`hLiquid`, `hVaporSat`, `hVaporSuperheated`), плотности `rhoSuction`/`rhoDischarge` (идеальный газ с коэффициентами сжимаемости 0.92/0.95), `dischargeTemp` (оценка конца сжатия по изоэнтропе с `etaIs=0.75`), `dTfromdP`, `cyclePoints` (**4 точки цикла**: перегрев на всасывании, конец сжатия, переохлаждённая жидкость, дросселирование).

### `pricing` — ценообразование
- **Файл**: `services/pricing.js`
- **Факторы** (`FACTORS`): мелочь 5 %, работы 30 %, профит 15 % — **все от суммы материалов**, не каскадом.
- **`computeTotals(materialsEur, discountPercent)`**: `материалы → +мелочь+работы+профит = Итого без НДС → −скидка = ВСЕГО`. Скидка ограничена 0–100 %.
- **`nextQuoteNumber()`** — номер вида `KP-{год}-{NNNN}` (последний номер за год + 1, с ведущими нулями).

### `polyfit` — генерация полиномов физической моделью
- **Файл**: `services/polyfit.js`
- **Ответственность**: для производителей без готовых коэффициентов (Bitzer, Copeland, Ridan, Invotech) генерирует полиномы capacity/power методом наименьших квадратов по физической модели объёмного компрессора.
- **Модель**: `Q0 = Vh/3600 · ηv · ρвс · Δh0`, `N = Q0 / COP`. `ηv` зависит от типа (screw 0.035 / recip 0.055 / scroll 0.045) и степени сжатия, с полом 0.55.
- **`generatePolyCoeffs`** строит сетку `tEvap ∈ [-40..5]`, `tCond ∈ [20..55]` и решает МНК (метод Гаусса с частичным выбором) → 10 коэффициентов.
- **Используется только в**: `db/seed.js` (`seedGeneratedCompressors()`).

### `db` — слой данных
- **Файл**: `db/database.js`
- **Ответственность**: единственное место, где определяется схема БД и открывается соединение. Экспортирует `{db, DB_PATH, syncOptions}`.
- **Таблицы**: `users`, `refrigerants`, `manufacturers`, `compressors`, `components`, `pipe_sizes`, `options`, `quotes`, `settings`.
- **`syncOptions()`** (вызывается при старте и в `seed`): UPSERT опций из `OPTIONS` в таблицу и **удаляет** коды, которых больше нет в определениях. Это ключевой механизм, позволяющий менять правила подбора без пересоздания БД.

### `OPTIONS` — единый источник истины для опций
- **Файл**: `db/optionDefinitions.js`
- **Ответственность**: массив-описание ~30 опций (корпус, шумоизоляция, виброгасители всас/нагнег, регулировка производительности, инвертор, отжим клапанов, обратные клапаны после КМ, маслоотделитель/маслоресивер/ЭРУМ, зимняя опция KVR+NRD+NRV, клапан до себя, обратный клапан на сливе, дифклапан, подогрев ресивера, ресивер, обратные клапаны, фильтр-осушитель DCL, вставка, глазок, шаровые краны, отделитель жидкости, фильтр SDF, сервисные краны, реле уровня, соленоид).
- **Ключевые поля**: `code`, `name`, `section` (раздел спецификации), `component_category`, `sizing`, `pipe_line`, `price_eur`, `auto_rule` (JSON), `mandatory`, `sort_order`.
- **Значения `sizing`**: `none`, `pipe`, `pipe_per_compressor`, `per_compressor`, `capacity`.

### `quotes` (таблица) — коммерческое предложение
- **Файл**: `db/database.js` + `routes/quotes.js`.
- **Ответственность**: хранение снимка расчёта (`input_json`, `result_json`) и статуса (draft → sent → approved/rejected).
- **Инвариант доступа**: клиент видит только свои КП; администратор — все; производственная спецификация и CSV доступны только после `approved` (или админу).

## Поток данных

### Поток 1: Подбор и расчёт (главный сценарий)
1. Пользователь на `/calc` заполняет форму (`views/calc.ejs`): хладагент, `requiredKw`, `tEvap`, `tCond`, перегрев/переохлаждение, корпус, режим (`auto`/`manual`), чекбоксы опций.
2. Клиентский JS (инлайн в `calc.ejs`) при выборе ручного режима делает `GET /calc/api/compressors?refrigerant=…&type=…&manufacturer=…` → `routes/calc.js` возвращает список моделей.
3. Сабмит `POST /calc` → `routes/calc.js` парсит тело в объект `input` и вызывает **`runCalculation(input, res.locals.user.discount_percent)`**.
4. `runCalculation` (`services/calc.js`):
   - `selection.autoSelect(...)` **или** ручной `compressorId` → выбранный набор;
   - `selection.evaluateSelection(...)` → характеристики (`sel.items`, `sel.totals`);
   - `piping.calcPiping(...)` → трубопроводы, из них `pipeSizes {suction, discharge, liquid}`;
   - `vibration.planAll(...)` → планы виброгасителей;
   - `options.resolveOptions(ctx, selectedOptions)` → позиции BOM по опциям (передаёт `vibrationPlans` в контекст, чтобы не пересчитывать);
   - сборка полной `bom` (компрессоры + корпус + `FIXED_ITEMS` + опции) и подсчёт `materials`;
   - `pricing.computeTotals(materials, discount)` → итоговая цена;
   - `refr.cyclePoints(...)` → точки цикла.
5. Результат рендерится обратно в `calc.ejs` (характеристики, компрессоры, трубопроводы, виброгасители, спецификация, стоимость). Цены видны только админу (`isAdmin` в шаблоне).

### Поток 2: Сохранение и оформление КП
1. Кнопка «💾 Сохранить как КП» повторно отправляет исходные данные как скрытые поля на `POST /quotes/save`.
2. `routes/quotes.js` **заново** вызывает `runCalculation(...)` (пересчёт), получает номер через `pricing.nextQuoteNumber()`, сохраняет `input_json` и `result_json` в таблицу `quotes`, редиректит на `/quotes/{number}`.
3. Просмотр — `GET /quotes/:number` (`quote-view.ejs`): проверка прав (клиент/админ), отображение.
4. Печать — `GET /quotes/:number/print` (`quote-print.ejs`).
5. Статусы — `POST /quotes/:number/status`: клиент может только `sent`; `approved`/`rejected` — только админ; при `approved` проставляется `approved_at`.
6. Производственная спецификация — `GET /quotes/:number/production` (`production.ejs`) и экспорт `GET /quotes/:number/production.csv` (CSV с BOM и калькуляцией, BOM-разделитель `;`, BOM-префикс `\uFEFF`, UTF-8).

### Поток 3: Регистрация и доступ
1. `POST /register` (`routes/auth.js`) → хэш `bcrypt`, вставка пользователя со `status='pending'`, `role='client'`.
2. `notifyNewRegistration(user)` (`bot/telegram.js`) отправляет админу карточку с кнопками `approve:{id}` / `reject:{id}`.
3. Callback-обработчики бота меняют `status` на `active`/`rejected`.
4. Fallback — веб-админка `/admin/users`: смена статуса и скидки клиента.
5. `POST /login` проверяет пароль и статус; при `active` устанавливает `req.session.userId`.

### Поток 4: Импорт каталога компрессоров из Excel
1. Админ на `POST /admin/import` загружает `.xlsx` (поле `file`) и выбирает производителя.
2. `routes/admin.js` читает первый лист через `XLSX.read`, ищет строку заголовков.
3. Для каждой строки (начиная с `headerRow+1`) парсит модель и коэффициенты по **фиксированным индексам колонок** (см. константы в коде: `[0]` модель, `[3]` хладагент, `[4]` Vh, `[6]` dSuction, `[7]` dDisch, `[8]` Imax, `[10..13]` границы tcond/tevap, `[14..23]` P_C (power), `[44..53]` M_C (mass), `[54..63]` C_C (capacity), `[64]` множитель).
4. `INSERT … ON CONFLICT(manufacturer_id, model, refrigerant_code) DO UPDATE` — идемпотентный upsert. Тип при импорте жёстко `'scroll'`.
5. Пропускаются строки без capacity-полинома (`r[54] == null`) или с несуществующим хладагентом; результат (`imported`/`skipped`) рендерится обратно.

## Неочевидные поведения и проектные решения

### Хитрости и инварианты
- **Порядок middleware для charset критичен.** Установка `Content-Type: text/html; charset=utf-8` происходит **после** `express.static` и **только если заголовок не задан** (`if (!res.getHeader('Content-Type'))`). Если поставить её раньше или без проверки — CSS/JS начнут отдаваться как `text/html`. Это явно прокомментировано в `server.js`.
- **Сессии — in-memory.** `express-session` без хранилища: при перезапуске сервера все сессии теряются. Cookie живёт 7 дней. Для продакшена понадобится store.
- **`res.locals.user` не переживает смену статуса.** Пользователь загружается по `userId` из БД на каждом запросе, но подставляется в шаблоны только при `status === 'active'`. Если админ отклоняет активного пользователя, тот мгновенно теряет доступ (сессия формально жива, но `user` = null → редирект на `/login`).
- **Обновление опций «на лету».** `syncOptions()` вызывается при каждом старте и **удаляет** из БД опции, отсутствующие в `OPTIONS`. Это значит: переименование/удаление опции в коде молча удалит её строку из БД. Единый источник истины — `db/optionDefinitions.js`, а не БД.
- **КП хранит снимок, а не ссылку.** `result_json` фиксирует результат на момент сохранения, но `routes/quotes.js` **пересчитывает** КП при `POST /quotes/save`. Если между расчётом на экране и сохранением изменился каталог/цены — сохранённое КП отличается от показанного.
- **Скидка берётся из профиля, а не из формы.** И в `/calc`, и в `/quotes/save` используется `res.locals.user.discount_percent` (задаёт админ). Клиент не может влиять на скидку через форму.

### State и мутации
- **Максимум состояния — в БД.** Сервисы в основном чистые функции; изменяемые данные — таблицы SQLite (единственный writer — сам процесс Express).
- **WAL-режим** SQLite (`PRAGMA journal_mode = WAL`) и **`foreign_keys = ON`** установлены один раз при открытии.
- **`db` — это `DatabaseSync`** (синхронный API). Все запросы блокируют event loop; это осознанно принято ради простоты (нагрузка низкая, один процесс).

### Обработка ошибок
- Роутеры `calc` и `quotes/save` ловят исключения сервисов (`try/catch`) и рендерят `error`-страницу или форму с `error`.
- **`runCalculation` бросает ошибки** (не возвращает `null`): нет хладагента, нет температур, `tCond <= tEvap`, «Не найдено подходящих компрессоров», «режим вне диапазона полинома». Это важно: невозможно «тихо» получить неверный расчёт — он падает явно.
- Глобальный обработчик ошибок в `server.js` рендерит `error.ejs` (500), 404 обрабатывается отдельно.
- **Telegram-бот не критичен**: без токена `startBot()` просто логирует сообщение и выходит; `notifyNewRegistration` молча ничего не делает при отсутствии бота.

### Производительность
- **`autoSelect` полный перебор** — для каждой модели × каждое количество 1..maxQty. При большом каталоге (после Excel-импорта) это может быть заметно, но каталог относительно невелик.
- **Полиномы парсятся из JSON при каждом вызове** (`parsePoly`). Кэша нет — при частых вызовах в цикле автоподбора это лишний `JSON.parse`. Возможная точка оптимизации.
- **Индексы**: `idx_comp_cat (category, size_in)` на компонентах; `UNIQUE` на ключевых полях. Отдельных индексов под частые фильтры компрессоров нет.

### Внешние зависимости и их особенности
- **`node:sqlite` (встроенный модуль)** — экспериментальный в старых версиях Node; требует свежего Node 22+. Это осознанный выбор «без нативных зависимостей» вместо `better-sqlite3`/`sqlite3`. Это же подразумевает синхронный API.
- **`xlsx` (SheetJS)** — импорт завязан на **жёсткие индексы колонок** китайской Excel-структуры производителей (`型号` — «модель»). Формат совместим с листами `Refcomp_polynom` / `Xecom_polynom`. Любое изменение шапки в исходном файле ломает импорт — индексы не конфигурируемы.
- **Единицы полиномов различаются по производителю**: Refcomp — в кВт (`poly_multiplier=1`), Xecom — в Вт/кг-в-час (`poly_multiplier=1000`). Поле `poly_multiplier` — «делитель для перевода в кВт». Это критично и ловушка при добавлении новых данных.
- **`telegraf`** подключается лениво, только при наличии токена (через `require` внутри `startBot`). Бот запускается через long-polling (не webhook).

### Физика и допущения (нетривиальные)
- **Полином AHRI валиден только внутри диапазонов** `min/max_tevap` и `min/max_tcond`. `compressorPerformance` возвращает `null` вне диапазона. Если для ручного режима пользователь выбирает модель вне диапазона — `evaluateSelection` бросает исключение.
- **Допуск автоподбора 0.98 по мощности**: компрессор считается «покрывающим» требуемую мощность уже с 98 % (учёт погрешности). Верхний предел превышения — 60 % (иначе вариант отбрасывается).
- **`ηv`, `COP`, энтальпии — упрощённые модели**, а не CoolProp. В README явно указано: для финальной верификации — CoolProp / данные производителей. Энтальпии линейны по температуре (`h = h_f0 + cp·T`), теплота парообразования зависит от температуры как `latent0 − 0.35·T`.
- **Виброгасители: 3 компрессора → 6 позиций.** Это неочевидно и явно подчёркнуто в комментариях — размер определяется патрубком КМ, а при его отсутствии — по скорости для **индивидуальной** производительности, а не для общего расхода.
- **KVR подбирается по «ухудшенной» мощности**: `need = totalKw · kvrFactor(tCond)`, где коэффициент падает от 1.18 (при −40 °C) до 0.92 (при +10 °C) для не-R134a. Это поправка клапана по температуре конденсации.
- **`ratedCapacity` компонента интерполируется по tEvap** между двумя паспортными точками (t=10 и t=−30) с зажимом `f` в [0,1]. Это упрощение с поправкой только на одну из двух переменных.

### Что код о себе не объясняет
- **Промеджуточный статус `sent`** используется как «отправлено на утверждение», но в `admin-users.ejs`/UI нет уведомления админа о новом КП (в отличие от регистрации через Telegram).
- **`settings`** таблица объявлена в схеме, но **нигде не используется** — задел на будущее (глобальные настройки приложения).
- **`quotes` не хранит связь с конкретным агрегатом/версией каталога** — если цены компонентов изменятся, старые КП не пересчитываются (что правильно для снимка), но и не помечаются как устаревшие.
- **Импорт Excel не устанавливает поле `poly_current`/`poly_volume`** явно (они просто не заполняются), хотя схема их поддерживает. Ток и объёмный расход могут остаться пустыми для импортированных моделей.
- **`price_eur` при импорте по умолчанию** `defaultPrice` из формы (по умолчанию 1000 EUR) — цены не приходят из Excel.
- **CSV-экспорт спецификации** добавляет префикс `\uFEFF` (BOM) — чтобы Excel корректно открыл кириллицу.

## Рекомендуемый порядок чтения

1. **`README.md`** — даёт бизнес-контекст: что за продукт, стек, бизнес-логика цены, технические допущения.
2. **`server.js`** — показывает, как приложение собирается: middleware, права доступа, монтирование роутов, старт БД и бота.

4. **`services/calc.js`** — точка входа в бизнес-логику; читается как оглавление всего расчёта, после чего каждый `services/*` смотрится по необходимости.
